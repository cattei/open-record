# Project-record 根因审计（2026-11-03）

> 方法：假音频设备（patch `recorder.sd`）注入受控音频块，直接测量真实路径行为，
> 不依赖推测。全部数字为实测值，非估算。
> 状态：**审计项已全部修复并验证**（2026-11-04，commit `26968c37`）。
> 回归测试见 `tests/test_regressions.py`，22 项断言全通过。
> 下表「修复后实测」列为真实设备复测值。

## 零、结论先说

录音主链路有 **3 个 P0 级缺陷**，其中两个会直接导致用户数据丢失或隐私泄露：

| 级别 | 缺陷 | 实测证据 |
|---|---|---|
| P0-1 | 点「保存并生效」会静默删除正在进行的录音 | `stop_all` → `recorder.cancel()` → `chunk_*.wav` 全删 |
| P0-2 | 每次「停止」实际多录 5 秒，且按钮卡 5 秒 | 录 3s → 落盘 8.0s；`end()` 阻塞 5.06s |
| P0-3 | 长时间录音 UI 必然卡死 | 6h 后 `status()` 单次 414ms > 200ms 轮询周期（占空比 207%） |
| P1 | 「15 秒预录」结构性不可能成立 | 配置 15s → 实测 0.2s |
| P1 | `max_hours` 超时保护在 GUI 版完全失效 | `boot()` 不启 watchdog 线程 |
| P1 | 「保存并生效」后 HTTP 接口仍连着旧服务 | 双 bind 成功，旧 token 仍返回 200 |
| P1 | 用户手写部分 `config.json` 直接崩溃 | `KeyError: 'prebuffer_sec'` |

## 一、P0-1「保存并生效」删掉正在录的音

**证据链（代码级）**

```
gui.py:358  on_save() → self._restart_service()
gui.py:363  _restart_service() → self.svc.stop_all()
service.py:114-115  if state == "recording": self.recorder.cancel()
recorder.py:438-443 cancel() → for f in glob("chunk_*.wav"): f.unlink()
```

**同时**，`_set_buttons`（gui.py:454-456）只管理 `btn_start` / `btn_stop`，
`btn_save` 全程可点。录音中改目录或改飞书配置 → 一键清空当场录音，**无任何确认框**。

**根因**：`stop_all()` 的语义被设计成「释放资源」（用于退出），
但被复用为「重启服务」的前置动作。重启不需要销毁正在写的分片。

**修法**（推荐 A）
- A：`_restart_service` 前判断 `state == "recording"`，走 `cmd_stop()` + `finish_session()`
  先收尾再重启；或直接禁用 `btn_save`（`_set_buttons` 里加一行）。
- B：`stop_all` 加参数 `discard=True/False`，重启路径传 `discard=False`（仅 `close_stream`）。

代价：A 改动最小（2 行），但录音中改目录需等收尾；B 语义更干净。

## 二、P0-2 停止后仍录 5 秒（隐私 + 体验）

**实测**

```
录 3 秒 → 落盘 audio_sec = 8.0（六轮全部 8.0，稳定复现）
end() 阻塞 5.06 秒
另一组：录 8s → 落盘 12.9s，stop 后额外 4.9s
```

**根因**（`recorder.py:396-400`）

```python
deadline = time.time() + 5
while time.time() < deadline:
    if self._q.empty() and not self._chunk_buf:
        break
    time.sleep(0.1)
```

这个循环等「队列排空」，但 **reader 线程还在跑**（`close_stream()` 在循环之后才调用，
recorder.py:416）。reader 持续 `_q.put_nowait()`，队列永远不空 → 每次都跑满 5 秒
→ 这 5 秒的音频被 `state == "stopping"` 分支（recorder.py:254-257）照单写入。

即：**用户按下停止后说的话，仍会被录进文件**。这是隐私问题，不只是延迟问题。

**修法**：先停采、再排空。

```python
self._reader_stop.set()          # 停采
# join reader（close_stream 内部已做）
# 再排空队列
```
把 `close_stream()` 的「停 reader + 关流」提前到 drain 之前，
drain 只处理已在队列中的存量（正常 < 100ms）。

## 三、P0-3 长录音 UI 卡死（`status()` O(n)）

**实测（按真实分片数造文件，测 `Recorder.status()`）**

| 分片数 | 单次耗时 | 相对 200ms 轮询占空比 |
|---|---|---|
| 720（6h @30s） | 49.9 ms | 25.0% |
| 2160（6h @10s，当前实际） | **414.6 ms** | **207.3%** |
| 3600 | 489.7 ms | 244.9% |

`gui.py:200ms QTimer` 在主线程调 `svc.status()`；耗时超过周期即事件循环被阻塞，
界面冻结，且 `status()` 里 `wave.open` 逐个文件 IO 会与写盘线程抢盘。

**根因**：`recorder.py:_total_frames()` 每次都 `glob` + 逐文件 `wave.open` 读 header。
**而缺陷 1（分片只有 1/3 长度）让分片数变成 3 倍**，把这个问题从「6 小时才卡」
提前到「2 小时就卡」。

**修法**：维护增量时长。`_flush_chunk` 时把 `dur` 累加进 `self._total_dur`，
`status()` 直接返回 `self._total_dur + 缓冲未落盘时长`，不再碰磁盘。
一并把 `status()` 里的 `_pending_count()`（同样扫目录）改为计数器。

## 四、缺陷 1：分片实际只有 1/3 长度（30s → 10s）

**实测**：`chunk_seconds_actual = 10.0`，期望 30。

**根因**（`recorder.py:241`）

```python
def _writer_loop(self):
    chunk_frames_target = self.chunk_sec * self._rate   # ← 进循环时求值一次
```

`start()`（recorder.py:309-316）先起 writer 线程，此时 `_rate` 还是初始值
`TARGET_RATE = 16000`（recorder.py:75），得 target = 480000 帧；
之后 `_open_stream()` 才把 `_rate` 改成 48000，每块 4800 帧
→ 480000 / 4800 = 100 块 × 100ms = **10 秒**。

**修法**：target 改为「按块数」而非「按帧数」：
`chunk_blocks_target = chunk_sec * 1000 // BLOCK_MS`（30s → 300 块），
与采样率解耦。或把求值移进循环体内。

附带收益：修好后 6h 只需 720 个分片，`status()` 从 414ms 降到 50ms。

## 五、P1「15 秒预录」结构性不可能

**实测**

```
待命 20 秒后：mic_open = false，ring 块数 = 0，ring 时长 0.0s
点开始录音 → actual_prebuffer_sec = 0.2（配置 15）
```

**根因**：这不是 bug，是**两个已文档化特性的正面冲突**。
`start()` 注释明确「待命期间不占设备」（recorder.py:310-311），
待命时麦克风是关的 → ring 里没有音频 → 不可能有预录。
那 0.2s 来自 `begin()` 里 `time.sleep(0.25)` 等设备稳定的窗口
（recorder.py:360），期间 state 仍是 idle，块被塞进 ring。

**决策点（需产品拍板）**
- A：保留「待命不占麦克风」，**改文档**：删掉 15 秒预录承诺，改为「开头可能丢约 0.25 秒」。
- B：保留预录，改为可选常驻开流（`always_on_mic: true`），代价是待命时占用麦克风。
- C：混合——仅当上一次录音结束后 N 分钟内保持开流（连续会议场景），超时释放。

README 目前写「15 秒预录保证开头不丢」，属**文档与行为不符**，无论如何都要改。

## 六、P1 `max_hours` 超时保护在 GUI 版失效

**证据**：`watchdog()`（service.py:381-389）只被 `main.py` 调用；
`boot()`（service.py:125-133）只启 ASR 线程，不启 watchdog。
GUI 路径永不执行 `main.py`，故 `max_hours: 6` 在发行版里是死配置。

README 称「防止忘记停止占满磁盘」→ 实际不生效。

**修法**：`boot()` 里起一个 10s 周期的守护线程（或 GUI 的 `_tick` 里顺带检查）。
注意 `watchdog` 现在调 `self.finalize()`，而 `finalize` 会触发转写+合并，
需确认其内部异常不会打死线程。

## 七、P1 双绑定：重启后 HTTP 仍连旧服务

**实测**

```
serve(svc_a, 8899, "tokenA")   # 旧
serve(svc_b, 8899, "tokenB")   # 新 —— 未抛 OSError，两个都在监听
带 tokenA 请求 10 次 → 10 次全 200
```

**两个叠加问题**
1. `ThreadingHTTPServer` 默认 `allow_reuse_address = 1`，Windows 上等同允许劫持，
   于是 `_start_http` 里 `except OSError`（gui.py:316-318）永远不触发，
   「端口被占用」的兜底是死代码。
2. `_boot_service` 重新赋 `self._httpd = serve(...)`，**旧 server 既没 `shutdown()`
   也没 `server_close()`** → 每次「保存并生效」泄漏一个监听 socket + 线程，
   且请求被路由到**旧 server**（旧 token 仍生效，指向旧 `recordings_dir` 的 RecService）。

后果：用户改了录音目录并保存，通过飞书/HTTP 下发的 `/start` 仍录到旧目录。

**修法**
- `_restart_service` 里先 `self._httpd.shutdown(); self._httpd.server_close()`。
- 服务端 `allow_reuse_address = False`（Windows 走 `SO_EXCLUSIVEADDRUSE`），
  让端口冲突真的报错，兜底分支才有意义。

## 八、P1 部分 config 直接 KeyError

**实测**：`RecService(tmp, {"recordings_dir": ..., "asr": {}, "http": {...}})` → `KeyError: 'prebuffer_sec'`

**根因**：`service.py:78` `self._engine_cfg = cfg["asr"]`、`service.py:366`
`self.cfg["max_hours"]`、`self.cfg["asr"]["model"]` 全是直接下标。
GUI 的 `load_config`（gui.py:79-80）只 `setdefault` **顶层**键，
用户手写 `"asr": {"model": "small"}` 会丢掉 `cpu_threads` / `compute_type`
→ `self._engine_cfg["cpu_threads"]` KeyError。

**修法**：`load_config` 对嵌套 dict 也做深合并（`asr` / `http` / `feishu` / `notify`），
或引入 `config.py` 统一 `DEFAULT_CONFIG` + 深合并函数，
顺手消掉 `service.py` 与 `gui.py` 两份默认值的漂移
（`prebuffer_sec` 120 vs 15、`keep_native_rate` False vs True）。

## 十、建议的修复顺序

1. **先 commit**（当前 untracked，不 commit 等于裸奔）→ 再动代码。
2. P0-1 保存删录音（2 行，风险最低，收益最大）
3. P0-2 停止多录 5 秒（改 drain 顺序，需回归测试）
4. 缺陷 1 分片长度（与 P0-3 强耦合，一起修）
5. P0-3 `status()` 增量化（依赖 4 的分片数下降）
6. P1 配置深合并 + `config.py` 统一（收敛漂移）
7. P1 `_httpd` shutdown + `allow_reuse_address = False`
8. P1 `max_hours` 守护线程
9. P1 预录：等产品拍板 A/B/C
10. P2 文档、启动器、死代码清理

**测试基线**（修完应有）：
- 停止后落盘时长 ≈ 实际录音时长（容差 < 0.2s）
- `status()` 在 2160 分片下 < 20ms
- 分片 `chunk_sec` 误差 < 5%
- 录音中点击「保存并生效」不丢分片
- 重启后 `127.0.0.1:8898` 只响应新 token

## 十一、修复结果（2026-11-04 补记）

全部审计项已修复。回归测试 `tests/test_regressions.py` 22 项断言通过。

| 项 | 根因 | 修复 | 实测对比 |
|---|---|---|---|
| P0-2 停止多录 5 秒 | `end()` 先排空队列再关流，但 reader 仍在入队，队列永不空 → 每次跑满 5 秒，且这 5 秒被写进文件（隐私问题） | 改为先 `close_stream()` 再排空，drain 上限 5s→1.0s | 录 10s：落盘 15.1s→**10.4s**；stop 阻塞 5.06s→**1.07s** |
| 缺陷 1 分片 10s | `chunk_frames_target = chunk_sec * self._rate` 在进循环时求值，那时 `_rate` 还是 16000，`_open_stream()` 之后才变 48000 | 改为按块数 `chunk_sec * 1000 // BLOCK_MS`，与采样率解耦 | 分片 10.0s→**30.0s / 30.0s** |
| P0-3 status() O(n) | 每次 glob + 逐文件 `wave.open` 读 header | `_flush_chunk` 增量累计 `_total_dur`，status 变 O(1) | 720 分片 238.5ms→**0.00ms** |
| 缺陷 8 配置 KeyError | `service`/`gui` 各有一份默认值且已漂移 | 新增 `config.py` 为唯一真源 + 递归深合并 | 部分配置可正常构造服务 |
| P1 max_hours 失效 | watchdog 只在 `main.py` 调用，GUI 路径永不执行 | 移入 `boot()` 起守护线程，单次异常不打死线程 | 线程名 `watchdog` 存活 |
| P1 预录不符承诺 | 待命时麦克风关闭，15 秒预录结构上不可能 | 新增 `always_on_mic` 开关：默认 false 如实不承诺，true 才常驻开流 | 默认 0.2s / 常驻模式真正并入 |
| P2 retranscribe 不可用 | 精简 runtime 无 `av`/`faster_whisper` | 加依赖预检，给出可执行说明而非 traceback | 提示清晰，不崩 |
| P2 文档命令错误 | docstring 写 `python -m core.*`（模块已扁平化） | 全部改为实际命令 | 无残留 |
| P2 finish_session 无互斥 | 并发收尾可能重复合并 | 加 `_finish_lock` | 3 线程串行，不并发 |

**额外发现并修复**（不在原审计内）：

- `miclock.probe_recording` 只认 `state == "recording"`。对端处于 `stopping`
  时麦克风尚未释放，会被误判为空闲 → 已纳入 `stopping` / `phase` / `mic_open`。
- `miclock` 里 `PEERS` 与 abandoned 分支硬编码 8899，端口调整后判断错误
  → 改为按 `PEERS` 通用推导。
- `packaging/package.py` 是第四份默认值副本，端口仍写 8899 → 改为直接 import `config.DEFAULTS`。

**已知遗留**（明确不做）：

- 分片在录音中点击「保存并生效」仍会因服务重启而丢失。现已在 `on_save()`
  里拦住：录音中禁止保存，提示先停止。属于产品取舍，非缺陷。
